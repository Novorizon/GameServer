# 独立 TCP：首次明文与 AES-GCM 实验（历史记录）

最新比较请看 [TCP / AES-GCM / TLS 三轮同条件实测](tls-comparison.md)。本页保留首次单轮原始结果；新测试使用固定请求数预热，并新增固定速率通信阶段，判断 AES 与 TLS 的差异应使用新报告中的同一批数据。

测试日期：2026-11-04（北京时间）。本报告只比较当前同一套二进制的两个配置：**纯 TCP** 与 **TCP + AES-GCM**，两组都没有 TLS、WebSocket 或 HTTP 升级。不能把它与此前 90 MB、100 MB、500 MB 等不同实验条件的数字拼成“优化前后”。本次未重新测量旧 TLS 版本，因此不声称具体的 TLS 优化百分比。

## 固定条件

- Linux x64，主机型号 AMD EPYC 9V74；当前沙盒可用 5 个逻辑 CPU，宿主可见内存约 33.3 GiB。服务器绑定其中 4 CPU，负载客户端绑定另 1 CPU；这不是用户线上 4 核 2.5 GHz / 4 GB 机器的复现。
- .NET SDK 10.0.403、运行时 10.0.14，Release，同一批 DLL SHA-256 完全相同，系统默认分配器；没有切换 jemalloc、强制 GC 或非托管接收缓冲区。
- 服务器使用 3 GiB GC 堆上限与采样式 4 GiB RSS 看门狗。沙盒没有可写内存 cgroup，**并未实施真正的整进程 4 GiB 硬限制**；这不能替代在实际 4 GB 机器上的验证。
- 每组独立重启服务器与客户端，真实 JWT 校验和 MySQL 账号查询，8000 个不同测试账号，约 700 登录/秒。双方通过本机回环通信。
- 128 个请求工作任务遍历 8000 在线客户端，先心跳预热 3 秒和 1 KiB 回显预热 3 秒；随后空闲 15 秒、心跳 20 秒、1 KiB Protobuf 回显 20 秒、空闲 10 秒，再断开并观察回收 7 秒。1024 字节数据经 Protobuf 封装后负载为 1027 字节。
- 两组都启用零字节读取、相同托管缓冲池与资源预算；AES 只额外增加每连接 40 字节初始化和每帧 16 字节标签。
- 回显处理器只由测试程序 `--serve` 注册；正式 Host 不开放测试回显。回显测试不代表正式游戏的完整数据库写入、场景逻辑或广播负载。

## 内存结果

统一单位 **MiB = 1,048,576 字节**。下表均为服务器单个进程 RSS，**不含客户端、MySQL 和内核 socket 内存**。阶段末值为该阶段最后一次采样，峰值为约 250 ms 间隔采样的最大值，不保证捕获极短瞬时尖峰。

| 相同测量阶段 | 纯 TCP | TCP + AES-GCM |
| --- | ---: | ---: |
| 8000 登录完成，阶段末 RSS | 129.5 MiB | 148.3 MiB |
| 同样预热后空闲 15 秒，阶段末 RSS | **155.6 MiB** | **170.0 MiB** |
| 持续心跳 20 秒，RSS 峰值 | 173.7 MiB | 192.4 MiB |
| 1 KiB 回显 20 秒，RSS 峰值 | 170.0 MiB | 190.1 MiB |
| 通信后继续空闲 10 秒，阶段末 RSS | 162.0 MiB | 175.0 MiB |

在本次 8000 连接空闲阶段，加密版增加约 **14.4 MiB RSS**；这是整体进程观测差，包含加密对象、运行时和分配器状态差异，不能直接解释为精确的单连接算法内存。空闲接收缓冲区使用量两组均为 0。

资源遥测每 5 秒采集一次，空闲阶段末最近采样的托管内存估计约为 47.5 / 34.6 MiB，GC committed 约为 70.1 / 64.1 MiB（纯 TCP / AES）。两者与 RSS 口径不同；GC 发生时点也不同，不能从加密版托管估计更小推断加密节省内存。`heap_last_gc` 是上次 GC 的堆数据，可能陈旧，也不能与当前托管估计直接相减。

断开后，两组日志均确认 `Connections=0 Sessions=0 Players=0 ReceiveInUse=0 SendInUse=0 PendingSend=0`。回收窗口中 RSS 没有立即恢复到启动值；这包括运行时/分配器保留，以及尚未触发回收的对象，不能仅凭 RSS 判定连接泄漏。7 秒回收观察并不构成长时间反复重连稳定性证明。

## 同负载形式的吞吐和 CPU

CPU 百分比按分配给服务器的 **4 核总容量**归一化，100% 表示四核全部占满。CPU/请求是服务器进程累计 CPU 时间除以完成请求数；延迟为客户端端到端往返，含排队。

| 阶段 / 指标 | 纯 TCP | TCP + AES-GCM |
| --- | ---: | ---: |
| 登录 8000 连接耗时 | 11.91 秒 | 11.66 秒 |
| 心跳吞吐 | 44,652 请求/秒 | 36,130 请求/秒 |
| 心跳服务器 CPU | 56.2% | 59.1% |
| 心跳服务器 CPU/请求 | 50.3 µs | 65.5 µs |
| 心跳 p99 往返 | 22.70 ms | 24.35 ms |
| 1 KiB 回显吞吐 | 41,735 请求/秒 | 32,098 请求/秒 |
| 1 KiB 回显服务器 CPU | 57.9% | 55.5% |
| 1 KiB 回显服务器 CPU/请求 | 55.5 µs | 69.2 µs |
| 1 KiB 回显 p99 往返 | 23.50 ms | 25.50 ms |

这是固定 128 在途工作任务的闭环测试，两组负载形式相同，实际完成请求数不同。AES 增加 CPU/请求，并降低此条件下的吞吐；不能因为某阶段总 CPU 更低便称它更快。客户端也只有 1 核，回环、客户端处理和队列会影响测出的吞吐，因此本表不代表服务器极限容量或生产容量承诺。

两组 8000 连接均成功，客户端失败数为 0，服务器和客户端正常退出，资源看门狗无违规。默认连接上限恰为 8000；本次没有证明可接受第 8001 个同时在线的游戏连接。服务就绪探针会额外建立并关闭一个 TCP 连接，因此服务端累计 Accepted 计数为 8001，并不表示同时在线超过 8000。
